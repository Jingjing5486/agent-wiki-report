Knowledge organization & retrieval

Agent Wiki通过知识组织改进检索质量与效率

以缩短检索时延、提高检索准确率为目标，探索不同的知识组织方式，以及利用这些组织结构进行检索的方法。重点比较文档树、摘要层级、语义图与类型化 Wiki 如何组织信息、建立关联并支持检索。

已有依据：论文 / 官方资料 / 本地审计设计建议：待实现或对照验证效果边界：不预设性能提升
阅读主线：问题与目标 → 方案空间 → Wiki 文件结构 → 生成方法 → 检索方法 → 总结与判断。正文数字引用可跳至文末资料；技术细节可展开阅读。
01

问题与调研目标

从扁平化 chunk 检索，转向对知识组织方式与检索方法的探索。

传统的扁平化 RAG 将文档切分为多个 chunk，在全量 chunk 构成的检索库中，将 query 与 chunk 进行匹配，选出相关片段供模型回答问题。这种方式主要依赖问题与独立片段之间的相关性，存在两个值得改进的问题：[23][8]

  1. 检索范围大，可能带来计算开销与冗余。每次查询都面向全量 chunk 查找，随着语料规模增长，候选检索和后续处理的开销可能增加；内容相近或重复的片段也可能被反复召回、读取。
  2. 没有充分利用片段之间的语义关系与文档层级。chunk 被作为相对独立的单元检索，片段之间的主题联系、跨文档关联，以及文章的章、节、小节结构没有充分参与检索过程，难以据此缩小查找范围或找到关联证据。[23][8]
最终目标：缩短检索时延，提高检索准确率。

为此，本报告从知识组织方式入手，重点调研两个相互关联的问题：知识可以如何组织，以及检索方法如何利用这些组织结构。围绕文档树、摘要层级、语义图和类型化 Wiki 等方式，比较它们如何组织信息、建立关联，并支持范围选择、逐层定位和关联检索。

02

方案空间：知识结构 × 检索方法

知识结构决定信息如何组织，检索方法决定如何利用这些结构查找信息。

2.1 知识结构

结构节点构建方法与结构特点
A0 · 扁平片段池chunk将文档切分为片段，分别建立检索索引。
A1 · 文档结构树文档、章、节、小节提取或重建文档目录，以父子关系连接章节，并记录原文范围。[5]
A2 · 派生摘要层级原始 chunk、各层摘要对片段聚类并递归生成摘要，形成自底向上的语义层级；软聚类允许多重归属。[4]
A3 · 语义图实体、概念、原文片段等抽取关系并连接节点；部分方法进一步形成社区及社区摘要。[6][7]
A4 · 类型化 Wiki概览页、章节页、主题页、来源页按页面类型组织内容，通过目录、主题链接与来源引用连接文档内及跨文档知识。[8][23]

2.2 检索方法

方法检索过程结构利用方式
B1 · 平铺打分query → 词法 / 向量 / 混合检索 → 相关节点将节点放入共同候选集打分；候选可以包含不同层级的内容。
B2 · 层级导航选择上层节点 → 进入子节点 → 逐层定位利用父子关系逐步缩小候选范围。
B3 · 图检索与扩展定位种子 → 关联扩展、图传播或社区检索利用语义关系连接证据；不同方法可采用邻接扩展、PPR或社区摘要等机制。
B4 · Agent 工具循环搜索 → 读取 → 根据证据继续搜索、跳转或回退根据中间结果动态选择路径，可组合调用B1、B2、B3。

技术补充：RAPTOR 的两种查询方式

Tree traversal：先在顶层选择相关节点，再只在已选节点的孩子中继续选取，逐层下降，组合选中节点文本。Collapsed tree：将各层节点放到共同候选集合中检索，允许同时选择不同抽象粒度的内容。[4]

论文 Figure 3 在 QASPER 的20篇文档子集上比较两种方案，并据此选择 collapsed tree 用于主实验。这个结果支持“多粒度表示可能有价值”，却不是“逐层剪枝已证明带来加速”的证据。软聚类还允许多重归属，因此其层级不应机械等同于文档目录树。

03

Agent Wiki：文件组织与数据 Schema

概览页提供入口，概念页组织知识，源页保留依据；分类方式随语料确定，页面契约保持明确。

Karpathy 的 LLM Wiki 提出：在原始资料与用户之间，建立一套由 LLM 持续整理的 Markdown 知识库，将摘要、主题综合和交叉引用保存为可复用的页面。其架构区分原始资料、生成的 Wiki，以及规定文件格式和维护约定的 schema。这里介绍的是这一组织思路，以及受其启发的 LLM-Wiki 论文和 llm-wiki-compiler 实现。[24][23][9]

3.1 基本组织：概览页 / 概念页 / 源页

组成主要内容作用
概览页知识范围说明、分类目录、页面链接及简短描述；以index.md作为主要入口先了解知识库包含什么，再找到相关页面。
概念页 / 主题页围绕实体、事件、概念或主题整理的内容，附相关页链接与引用跨来源综合知识；一个页面可以关联多份资料，一份资料也可贡献多个页面。
源页 / 来源档案原始文章、PDF、解析后的Markdown或页级JSON，以及可选来源摘要保留可回查依据；来源摘要与完整原文应能区分。

这三类是内容职责，目录名不必统一。概念页可以按语料分成 entities/、events/ 等目录，也可以不设二级分类，直接放在 topics/ 或 concepts/ 下。页面 schema 需提前由人定义；具体页面及其分类可在编译时结合语料形成，但必须遵循预先约定的字段、类型与分类扩展规则。以下是本报告的通用组织示意。

项目/
├── schema.md                 # 页面字段、类型、链接、引用与目录约定
├── wiki/
│   ├── index.md              # 知识范围 + 导航目录
│   ├── concepts/             # 多个主题页；可按需要改为分类目录
│   │   ├── 主题A.md
│   │   └── 主题B.md
│   └── log.md                # 可选：构建与维护记录
└── sources/                  # 完整来源及定位信息
    ├── 原始资料.pdf
    └── 原始资料解析.md

目录树为通用示意，不是某篇论文或某个项目的固定要求。schema.md也可由AGENTS.md、JSON配置或程序类型定义承担。Karpathy明确将具体目录和格式留给领域与实现决定。[24]

3.2 index.md 应包含什么？

index.md 是内容导航：通常包括知识库的范围概述、分类及其含义、页面链接和一行摘要，也可附更新时间、别名或来源数。页面较多时，根索引先列分类，各目录再用 _index.md 或 index.md 列出页面；不分类时，根索引直接列出所有主题。[24][23]

3.3 例一：LLM-Wiki 按语料形成分类目录

LLM-Wiki论文附录E展示了2WikiMHQA语料的六类目录：concepts、geography、history、media、organizations、people。它们是主题分类，并非六种统一实体类型。根索引概述范围，分类索引列出页面；人物页再连接相关人物及来源。[23]

wiki/
├── index.md
├── concepts/          # 抽象概念
├── geography/         # 地理
├── history/           # 历史
├── media/             # 作品
├── organizations/     # 组织
├── people/
│   ├── _index.md
│   ├── John-V-Prince-of-Anhalt-Zerbst.md
│   └── Ernest-I-Prince-of-Anhalt-Dessau.md
└── sources/
    ├── digests/       # 段落级摘要
    └── articles/      # 完整原文

依据论文附录E缩写；其他知识目录同样有分类索引。六个目录名及两个页面名来自论文示例。

论文的知识页格式包括 type / created / updated / aliases / tags、摘要、关键事实、关联页面与来源。其John V示例通过父子关系链接Ernest I页面，展示了“读到一个实体后继续寻找关联信息”的组织方式。可变的是类别与目录，明确的是每类页面应具备的字段、链接和出处。[23]

因此，另一批以人物、机构和活动为中心的资料，可以采用 entities/ + events/；这属于按数据设计的方案，而不是上述2WikiMHQA示例的原样目录。

3.4 例二：llm-wiki-compiler 的主题页、查询页与持续更新

本地编译器采用默认的 concepts + queries 结构：wiki/concepts/ 保存从来源整理的主题页，wiki/queries/ 保存选择回写的问答结果。主题页不必预先分成行业或实体目录。不同来源中归到同一概念标识的内容进入同一页面，页面之间通过 [[wikilinks]] 连接。实现按概念标题生成的slug归并，并非自动保证所有同义主题都能合并。[9][10]

项目/
├── sources/                    # 输入Markdown来源
├── wiki/
│   ├── index.md                # Concepts + Saved Queries，含链接与摘要
│   ├── concepts/               # 从来源整理、融合的主题页
│   │   ├── 腾讯营销服务业务.md
│   │   ├── 腾讯股份回购.md
│   │   └── 腾讯ai战略投入与商业化.md
│   └── queries/                # 通过query --save保存的问答页
│       └── 问题对应的slug.md     # 文件名示意
├── log.md                      # 查询等活动记录
└── .llmwiki/
    ├── state.json              # 来源及编译状态
    ├── schema.json             # 可选：页面类型与链接要求配置
    └── candidates/             # 启用review时的待审核候选

具体例子：腾讯营销服务业务。本地这一主题页的 sources 列出三份来源：腾讯2025年第二季度及中期业绩公告、招银国际腾讯业绩点评、腾讯2024年第四季度及全年业绩演示。正文按分部定位、收入增长、盈利能力、AI应用等小节组织，而不是为每份报告各写一张同名页面。[26]

来源A公司公告腾讯2025Q2及中期业绩
来源B研究报告招银国际腾讯业绩点评
来源C业绩演示腾讯2024Q4及全年业绩
→
主题页腾讯营销服务业务正文分节 · 逐段引用 · 关联链接

该页frontmatter记录 title、summary、sources、kind、createdAt、updatedAt、tags、aliases，以及生成相关字段；本例的 kind=concept、provenanceState=merged。正文引用采用 ^[来源文件.md:起行-止行]。这里展示的是文件组织与溯源方式，不将模型生成页面中的全部财务内容视为已核验事实。[26][27]

查询页：把本次回答积累为后续上下文

除了从资料构建主题页，项目也支持将查询中的综合结果保存下来：使用 query --save，通过当前保存检查后，将答案写入 wiki/queries/<slug>.md，重新生成 index.md，并刷新启用且可用的embedding。目录中的 Saved Queries 分组使这些回答可被后续查询发现和复用。这补上了“使用Wiki也能积累Wiki”的一条路径。[29][25]

读取已有Wiki页面概念页与已保存查询页
→
综合生成回答基于检索内容组织答案
→
可选回写queries/query --save或审核后保存
→
复用更新目录与索引为后续查询提供上下文

查询页有自己的schema。固定版本代码写入 title、summary、type: query、createdAt，正文为生成的答案。它与概念页的 kind: concept 格式不同，应分别定义，不能假定两类页面具有相同frontmatter。[29]

持续演进：查询沉淀与来源更新是两条路径

更新来源影响的内容对应机制
一次新的查询与综合查询页、目录及相关检索索引query --save选择性保存回答，支持后续复用。
原始资料新增或变化受影响的概念页及其来源关系增量compile；refresh --stale对过期页面涉及的来源进行范围受限的重新编译。

这里的 self-evolve（持续演进）体现为知识积累和更新机制：既能保留查询产生的综合结果，也能随来源变化维护已有知识。普通查询不会自动回写；保存查询页也不会自动改写相关概念页，生成答案仍属于派生内容，不能替代原始来源。[29][30]

固定版本的保存与审核约定

本地版本5dc9102中，直接--save适用于默认profile；--save --review将回答放入候选区，审核前不写入正式查询页。保存前检查链接解析状态，但不等于验证答案事实正确。相同问题生成同一slug时，保存可替换对应查询页，并非自动保留多份历史版本。embedding刷新失败也不会撤销已保存页面。以上为代码行为说明，本轮没有执行查询或回写。[29]

3.5 增加文档结构页：SearchWiki 的扩展

主题页适合跨文档综合；对于有清晰章节的长文档，还可以增加按原文目录组织的文档概览与章节页。SearchWiki在 documents/ 中保存这类内容，topics/ 连接跨文档主题，sources/ 保留页级JSON。[8]

wiki/
├── index.md
├── documents/
│   ├── index.md
│   └── doc_id/
│       ├── index.md             # 文档概览、章节目录与页范围
│       └── part_i/
│           ├── index.md         # 本层章节目录
│           └── item_1_business.md
├── topics/
│   ├── index.md
│   └── risk_management.md       # 跨文档主题，链接相关文档和主题
├── sources/
│   └── doc_id.json              # 原文逐页记录：文本、页号及元数据
└── log.md

依据SearchWiki §3.2整理的结构示意；documents/doc_id/part_i/item_1_business.md为论文给出的路径示例，其余文件名用于说明组织方式。[8]

两种组织可以并存：文档结构页回答“某份资料的哪一章讲了什么”；主题页回答“多份资料围绕这个主题分别说了什么”。两者都需要指向sources中的具体依据。

3.6 页面 Schema：提前人为定义，编译时遵循

页面 schema 需要在生成 Wiki 之前由人定义，编译器与 LLM 按该约定填写内容。预先明确哪些字段必须存在、正文采用哪些章节、链接如何表示、来源如何引用。语料决定生成哪些页面、怎样归类；页面格式不能在每次生成时临时变化。

LLM-Wiki论文附录E规定知识页采用固定格式：YAML元数据 + 一行摘要 + 关键事实 + 关联页面 + 来源引用。下面按论文中的John V人物页作缩写示例，保留字段与章节名称，正文作中文转述。[23]

位置固定字段 / 章节内容约定
YAML元数据type、created、updated、aliases、tags页面类别、创建/更新时间、别名列表与标签列表。
正文入口一级标题 + 一行引用式摘要标明页面对象，简述其核心内容。
事实内容Key Facts分条记录关键事实。
页面关联Related Pages使用wikilinks指向关联页面，并说明关系。
来源引用Related Sources链接到对应来源记录，供进一步核验。

04

Wiki 生成方法

先看如何从空库生成第一批页面，再看不同系统怎样组织来源、主题与后续更新。

为了从头理解 Wiki 构建，先从本地 llm-wiki-compiler 看完整过程：准备来源和页面规则，编译成页面，再补齐链接与索引。之后对照 SearchWiki 如何利用文档目录联合生成摘要和主题，以及 LLM-Wiki 如何在持续导入时用错误反馈改进 Wiki。

4.1 llm-wiki-compiler：从空库开始，抽取概念并生成页面

首次运行时，来源目录中的文件都视为待处理来源。系统不要求来源先有统一的 PDF 目录结构；解析方式由项目提供。模型先从每份来源中抽取概念候选，程序把不同来源指向同一概念的候选合并，再让模型按页面规则生成概念页。收尾阶段生成 schema 规定的 seed pages、解析页面间链接并生成索引。之后再次运行时，系统只重做新增、变更或受影响的来源和页面。

输入：来源文件 + 页面 schema + 空 Wiki
首次建库：
  1. 找出所有待处理来源
  2. 对每份来源调用模型抽取概念候选
     输入：来源文本 + 当前概念索引
     输出：概念候选 + 来源证据
  3. 程序清洗候选，并合并同一概念的多份来源
  4. 对每个合并概念调用模型生成页面
     输入：概念信息 + 来源证据 + 页面 schema
     输出：页面候选
  5. 按审核策略写入页面；生成 schema 要求的 seed pages
  6. 解析页面间链接，修复可识别的断链，生成索引
输出：第一版 Wiki

后续更新：
  只处理新增/变更来源及受影响页面
  重做抽取、合并、页面生成和收尾链接/索引

这里模型负责“从来源中抽取概念”和“按 schema 写概念页”；程序负责变化检测、候选合并、审核/发布控制、链接解析及索引生成。schema seed pages 是项目配置的入口页等基础页面，不代表模型先生成了全部 Wiki 结构。[9][25][27]

4.2 SearchWiki：按文档目录生成摘要，同时登记跨文档主题

SearchWiki 面向有文档结构的语料。它先解析 PDF 页面并建立目录树，再调用大模型生成章节摘要和全局主题。主题页的链接分两种：主题与其他主题的关联由大模型在主题综合阶段选择；主题与文档概览的关联由程序根据该主题汇集到的来源自动生成。之后渲染程序把这些关联写成 Markdown 链接。

输入：一组 PDF / 文本文件
1. 解析页面，保存页码、文本和版面信息到 sources/
2. 提取目录和页码范围，建立 documents/ 章节树
3. 按文档编译单元调用大模型，联合生成章节摘要和主题登记操作
4. 汇总主题贡献；对每个规范主题调用大模型综合来源证据，并输入完整主题注册表
     输出：主题页段落 + related_topic_ids（最多5个，不含当前主题）
5. 由程序写入页面链接：
     - related_topic_ids 决定主题页之间的链接
     - 主题的来源贡献记录决定主题页链接到哪些文档概览
     - 文档目录树决定文档页和章节页之间的链接
6. 渲染器把页面关系写为相对 Markdown 链接；摘要引用保留页码并链接到 sources/
7. 生成根目录、子目录和主题索引，以及构建日志

因此，主题页之间的链接不是在第一次章节联合编译时生成的：该阶段负责登记主题及其来源。所有主题登记完成后，主题综合调用才根据全局注册表返回相关主题 ID；程序校验 ID 有效、不是当前主题后，再由渲染器写成页面链接。主题页到文档概览的链接不由大模型判断，而是根据主题的来源贡献记录自动建立。论文描述了最终页面关系；以上先后顺序和代码分工是本地 POC 的具体实现。[8] · 主题综合 Prompt（本地材料，未随网页发布） · 输出校验（本地材料，未随网页发布） · 链接渲染（本地材料，未随网页发布）

4.3 LLM-Wiki：逐段更新 Wiki，把错误经验用于后续批次

LLM-Wiki 适合持续导入新资料。每个 batch 再拆成 passage 逐条处理：先选相关旧页面，模型生成更新，系统校验后写入 Wiki。发现的问题进入 Error Book，转成下一批编译时使用的规则；定期再由模型修复全库中的语义问题。完整循环见论文附录 D。

输入：新资料 batch + 当前 Wiki + 来源档案 + Error Book
对 batch 中的每段资料：
  1. 根据目录索引选择相关旧页面
  2. 调用模型生成 Wiki 更新
     输入：当前资料段 + 相关页面 + 有效错误规则
     输出：页面更新 + 链接/目录更新
  3. 检查结构和内容依据
  4. 若发现错误：写入 Error Book；自动修复结构问题
  5. 将更新应用到 Wiki
定期执行：
  6. 调用模型修复全库语义问题
  7. 重新验证，并关闭已解决的错误记录

它和首次建库的区别是，主流程围绕“新 passage 到来后如何更新已有 Wiki”运转；错误记录会反馈到后续批次，形成持续修正循环。[23]

05

检索方法：从关键词匹配到 Agent 导航

检索方法可以作用于 Wiki 的不同页面和层级；Wiki 结构与底层召回算法可以组合使用。

第 02 节把检索方法归为四类：B1 平铺打分、B2 层级导航、B3 图检索与扩展、B4 Agent 工具循环。本节按这四类展开：BM25、Embedding 和 RRF 用于给候选内容排序；RAPTOR 展示了如何沿树的父子层级检索；Wiki 链接可以把检索从一个页面扩展到相关页面；Agent 则组合搜索、读取和跳转，并根据已获得的证据决定下一步。检索对象可以是主题页、文档页、章节页或来源片段，具体取决于任务需要的粒度。

5.1 平铺检索：对选定单元打分，直接取 Top‑k

最简单的做法是把所有选定单元放进一个候选集合，针对问题排序并取前 k 个。BM25 根据查询词与文本词项的匹配程度排序，适合明确实体名、术语、编号等词面线索；Embedding 将问题和单元编码为向量，再按相似度排序，适合表达不同但意思相近的查询。两者都可以检索整页或 chunk；也可以分别召回候选，再用 RRF 合并排名。SearchWiki 的 search_wiki 使用多查询 BM25 和 RRF 检索 Wiki 页面。[8]

RRF(d) = Σr ∈ 排名列表 1 / (c + rankr(d))
输入：问题 q，检索单元集合 U，返回数量 k
BM25：对 U 按 q 的词项匹配排序
Embedding：对 U 按 sim(embed(q), embed(u)) 排序
可选：将多组排名用 RRF 合并
返回：排名前 k 的页面或片段

平铺检索实现直接，检索器也容易替换；它本身不会沿目录或主题链接继续找相关页面。若初次召回漏掉关键证据，通常需要改写查询后再次检索，或增加其他导航机制。

5.2 树检索：利用父子结构逐层缩小范围

若 Wiki 有文档—章节—小节等父子结构，可以先对根层节点打分，再只在入选节点的子节点中继续打分。RAPTOR 的 tree traversal 正是这种方式：从根层开始，每层按 query embedding 相似度选 top‑k 子节点，并重复到叶子；最后合并沿途选中的各层节点作为回答上下文。因此，标准 tree traversal 并不会因为中间摘要看起来足够就自动停止，它按设定深度向下搜索。[4]

候选 = 根节点
已选 = []
对每一层，直到叶子：
  按 query 与候选节点的相似度排序
  本层选出 top-k 节点，加入已选
  候选 = 本层选中节点的子节点
返回：已选节点的摘要/正文

这里每层的相似度可以由 Embedding 计算；若使用词项检索，也可以在每层节点文本上运行 BM25。也就是说，树结构负责限制下一层的候选范围，BM25 或 Embedding 负责在当前候选中排序。用户提出的“程序按树筛选部分分支”与 RAPTOR tree traversal 思路相近，但“必须走到叶子”是 RAPTOR 这一路径的设定，不是所有层级检索的必然要求：程序可以自行设置最大深度或停止条件。

RAPTOR 还提出 collapsed tree：将所有层级的节点放入同一候选集合，直接从摘要节点和叶子节点中选相关节点，并在达到 token 预算后停止。它可以直接返回中间层摘要，不需要从根逐级走到叶子；代价是检索时要在整个树的节点集合中搜索。论文在其特定实验设置中采用 collapsed tree 作为主方法。[4]

5.3 图检索与链接扩展：从命中页面继续找相关页面

当页面之间存在主题关联、实体关系或显式 Wiki 链接时，检索可以先找到一个相关页面，再沿页面关系扩展邻居。例如，先命中公司主题页，再读取其链接的业务分部页或对应来源页。LLM-Wiki 将 link-following 作为检索操作；SearchWiki 的主题页也链接相关文档概览和其他主题。[8][23]

输入：初始检索得到的页面集合 S，页面链接图 G
候选 = S
重复 0 到 h 跳：
  将候选页面中符合关系/类型条件的链接目标加入候选
  可按 BM25 / Embedding 对新候选重新排序
  去重，并保留来源路径
返回：初始命中页及扩展得到的相关页面

链接扩展利用 Wiki 已有的关联结构，适合问题中间实体或关联页面尚未直接出现在查询中的场景。扩展范围需要控制跳数、页面类型或候选数量，否则主题页的高连接度可能带入大量无关页面。这里的约束方式是工程设计选择；论文支持链接遍历这一检索动作，但未规定统一的扩展评分公式。

5.4 Agent 检索：搜索、读取、跟链接，并判断是否继续

Agent 检索把一次 Top‑k 召回变成多轮过程。Agent 先调用搜索或目录工具，再读取返回页面；读取结果中的主题、章节和来源链接成为下一步入口。Agent 根据已经读到的内容决定继续搜索、沿链接跳转、下钻到来源页，还是停止并作答。这样可以在中间证据已经充分时停止，也可以在发现证据缺口时换方向或回退。SearchWiki 与 LLM-Wiki 都描述了这种基于中间观察的搜索—读取—验证过程。[8][23]

工具输入与返回在 Wiki 中的作用
search(query)输入查询，返回匹配的页面或文件路径及摘要。底层可以使用 BM25、Embedding 或二者融合；SearchWiki 的 search_wiki 使用多查询 BM25 + RRF。
read(path)输入页面路径，返回页面正文和其中的链接。读取主题页、文档概览或章节页，获取内容和后续跳转线索。
read_source(document, page_range)输入文档标识和页码范围，返回对应原文页。在摘要不足以支持答案时，定位到来源层核实细节；SearchWiki 以 read_page 读取页级 JSON。
list / grep输入目录或文本模式，返回文件列表或匹配行。浏览 schema 定义的目录，或在页面、主题和来源中查找精确术语。
输入：问题 q，Wiki 工具，调用预算 T
上下文 = []
重复，最多 T 轮：
  Agent 根据 q 和上下文选择 search / read / read_source / list / grep
  工具返回页面、正文、链接或来源证据
  将返回内容加入上下文
  如果证据足以回答：停止
  否则：改写查询、沿链接跳转、下钻或回退
输出：基于已读证据的答案和来源

这类方法能按证据充分性决定是否继续，但需要实现工具接口、路径与链接解析、调用状态和预算控制；这部分工程量高于单次 BM25/Embedding 查询。论文展示了相应的工具交互设计，但具体开发复杂度取决于工具数量、权限边界和 Wiki schema，不能仅从论文结果推断。

5.5 四类方法可以组合

这几种方式不是互斥的。一个实用组合是先用 BM25/Embedding 在主题页或概览页中召回入口，再沿 Wiki 目录或链接定位章节，最后读取来源页核对证据；Agent 可以负责决定何时执行每一步。对于已有结构的语料，也可以直接将每层节点用 Embedding 排序；或者把所有层级节点平铺检索。检索器决定“如何排序”，Wiki 结构决定“有哪些单元及其关系”，Agent 决定“下一步做什么以及何时停止”。

问题 → 检索入口（BM25 / Embedding / RRF） → 读取页面 → （按需）沿目录/链接下钻 → 来源核验 → 足够则回答

实施上可以从平铺 BM25 或 Embedding Top‑k 起步，再增加层级候选筛选或 Agent 工具循环；是否值得增加复杂度，应由目标任务的证据覆盖、时延和调用成本决定。这是基于上述论文机制提出的工程路线，不是论文已经验证适用于所有语料的结论。

06

总结与判断

方法选择取决于问题类型、资料形态、响应要求和知识复用频率。

目前有依据

不同结构面向不同检索任务

BM25、向量检索和混合检索提供直接的候选排序；文档树和 RAPTOR 面向长文档中的章节定位与多粒度理解；GraphRAG面向整个语料的主题归纳；SearchWiki展示了对多文档资料进行预编译，并训练Agent通过工具多轮导航的方案。论文证明的是特定任务和数据集上的可行性，不等于任一方案适合所有业务。[4][5][6][8]

仍待验证

在目标场景里的收益和代价

本项目需要验证：Wiki主题分类和Prompt能否减少后续整理时间；跨文件合并是否保留关键差异；Agent多轮调用是否改善证据召回，以及首字时间、排序等待和总响应时间增加多少。论文结果不能替代本地语料和问题集上的对照。

按具体工作场景选择方案

下表是面向部署的初步判断。语料规模只是一个条件；“5,000条以内”是便于定义试点范围的示例，不是论文给出的算法适用阈值。

具体场景优先试用为什么适合代价与风险
内部产品手册、制度库或客服知识库，试点不超过约5,000条记录；问题集中在常见、明确的事实查询，例如“报销上限是多少”“某功能在哪个版本上线”；要求尽快返回命中内容。BM25；用户常用说法与原文差异较大时，再加 Embedding 并用 RRF 合并。直接按问题找对应条目，结构和调用链较简单，适合作为低时延基线。跨多条记录的比较和归因能力有限；5,000条只是试点规模示例，实际效果还取决于记录长度、过滤条件、硬件和索引实现。
一份目录清楚的长报告、年报、合同或法规；用户经常问“某个指标在哪一节”“两个条款有什么区别”，并要求回到准确页码或原文。文档目录树 / PageIndex；如果问题需要整篇文档的多段信息，再评估 RAPTOR 的摘要树检索。先按目录定位章节，再读取页级证据；RAPTOR论文在 QASPER、NarrativeQA 和 QuALITY 等长文档问答任务上评估多粒度摘要检索。[4][5]依赖目录和页面解析质量；层级路由可能漏掉目录标题没有体现的证据，逐层读取也可能增加等待。
分析师反复比较同一公司不同年份的年报、业绩会和行业研究，例如追踪资本开支、云业务和 AI 商业化在不同来源、期间里的变化。带 documents / topics / sources 的主题 Wiki，例如 SearchWiki 的组织方式。把跨文件主题、文档概览和原文定位提前组织，适合反复复用同一批资料。SearchWiki在 ViDoRe、FinanceBench 和对话记忆基准上评估了 Wiki 导航方案。[8]建库和资料更新需要额外模型调用；主题过宽会混淆期间或口径，主题过碎又会降低复用价值，必须评估分类和引用质量。
管理层希望了解整个资料库的共性，例如“过去三年行业研究反复提到哪些增长驱动”“所有访谈的主要分歧是什么”，而不是找一条具体事实。GraphRAG的全局检索，或其他基于社区/主题摘要的全语料综合。问题本身要求归纳全库，而不是命中少数片段；GraphRAG论文正是针对整个语料的全局问题设计社区摘要和 map-reduce 回答。[31][6]图谱和社区摘要需要预处理；若实际问题只是查一个数字或条款，这类全局建模可能增加不必要的构建成本。
研究问题没有固定检索路径，例如需要先查公司计划，再核对后续披露；如果证据不足，还要换关键词、读关联主题或回到另一份文档继续查。Agent 调用搜索、读取、来源回查和链接跳转；底层检索仍可使用 BM25 或 Embedding。可以根据中间证据改写查询、选择下一份资料，并在证据足够时停止。SearchWiki研究了这种多轮工具导航。[8]规划和工具调用可能延后首字、增加排序等待、总响应时间及Token；若问题路径固定，Agent的动态决策可能没有必要。

推荐的研究顺序

  1. 先选一个准备部署的具体场景。明确资料类型、记录规模、典型问题、更新频率、答案引用要求和可接受的响应时间。
  2. 建立简单检索基线。在同一语料和问题集上测 BM25、Embedding 或混合召回的命中率、答案质量、排序等待和总响应时间。
  3. 针对复用需求调 Wiki 生成。小规模对照主题分类、同义主题复用和 Prompt；同时记录建库时间、输入/输出 Token、覆盖率、冲突保留情况和人工修订量，找出节省时间与算力的配置。
  4. 再判断是否部署 Agent。对同一批问题比较传统检索与 Agent 的证据召回、答案质量、首字时间、总响应时间和调用成本，确认多步导航带来的收益能否覆盖代价。
  5. 按结果部署并持续精调。锁定场景和评测问题，选择当前综合表现合适的方案，再根据真实失败案例调整分类、Prompt、索引和工具流程。
本版结论

先从明确场景和快速基线开始，再按证据决定是否增加 Wiki 结构或 Agent 导航。最终目标是在可接受的时延和成本下，稳定找到正确、可核验的证据。
